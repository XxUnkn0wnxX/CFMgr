## Hooks and schedules

The existing integration has several entry points, but they must share one controller. Merlin documents the boot, WAN, DDNS, mount, and unmount hooks in its [user-script reference](https://github.com/RMerl/asuswrt-merlin.ng/wiki/User-scripts).

| Hook/trigger | Current setup | Planned integration and preservation rule |
| --- | --- | --- |
| `services-start` | Registers the four Cloudflare jobs; also invokes YazDHCP, scMerlin/tailtaintdns, amtm history, BackupMon, and MerlinAU. | Separate JFFS blocks register saved eligible jobs independently of Entware and request detached work. Native DDNS/IP-Sync follow their own readiness gates; Cloudflared checks mount and returns/defer if absent. Off DDNS/IP-Sync blocks are absent. Preserve foreign content/control flow; no blocking wait, API or download in this hook. |
| `wan-event` | Unit `0`/`connected`, detached 20-second delay, then shared start; scMerlin receives the original arguments. | Preserve this tunnel baseline/default with configurable WAN selection/settle policy. Also request one coalesced detached shared-IPv4 discovery for enabled native features on the selected WAN's connected/reconnected event. Pass original arguments intact to other add-ons; no network work/wait in the hook. |
| `ddns-start` | Owns the custom Cloudflare DNS update and firmware completion; asynchronously notifies Access with the same IPv4. | Exactly one DDNS completion owner. Migrate recognized legacy CF provider code instead of appending a second updater. Unknown/custom hook content requires a reviewed integration path. |
| Access-only DDNS observation | Not separately configured in the reference. | Only while configured IP-Sync is On and CFMgr DNS is disabled, preserve the existing provider and add the owned IP-Sync observation block; route its candidate through the common resolver and do not report another provider's DDNS result. Standalone shared boot/WAN/discovery triggers also work when no DDNS provider exists. IP-Sync Off removes its observation block without touching the provider. |
| `post-mount` | Outside the primary reference: captured amtm/Entware mounting and other add-ons, including Scribe rotation registration. | Detached recheck only for actual Entware mount: resume eligible deferred Cloudflared/maintenance and eligible logging integration under health/enable/preference gates. DDNS/IP-Sync already operate independently; do not force sync or activate every service. Ignore unrelated mounts and preserve helpers/Scribe schedule. |
| `unmount` / `services-stop` | No CFMgr entries in the supplied reference. | Proposed bounded stop for the owned tunnel before its Entware volume disappears or services shut down. Match the actual Entware mount; keep hook duration bounded. |
| Watchdog/manual/update/restore | Existing watchdog, manual restart, and updater converge on shared lifecycle helpers. | All future service transitions use the same locks/readiness/stop/start implementation. |

Use stable comment identifiers such as `# CFMgr DDNS BEGIN` / `# CFMgr DDNS END`, with separate `IP-Sync`, `Cloudflared`, `Maintenance` and shared `NativeIPv4` blocks plus a private ownership manifest. The shared native block/job remains only while at least one valid DDNS/IP-Sync feature is On. This allows one feature to be removed without deleting another feature's calls. For example, the markers in a shared startup hook can look like this (illustrative; dispatch code is not implemented yet):

```sh
# CFMgr DDNS BEGIN
# CFMgr-owned DDNS startup/scheduler dispatch goes here.
# CFMgr DDNS END
```

Re-running install/repair must not duplicate blocks. Remove/replace only the exact identified CFMgr-owned block; never replace a whole populated hook, strip all matching words, or delete another add-on's markers. Preserve unrelated content, shebang, argument forwarding, existing branch/exit/return behavior, executable mode, and POSIX shell syntax. Choose a reachable insertion point instead of appending after an existing exit. Stage edits, syntax-check the complete hook, compare its current content again under the appropriate lock, and atomically replace only when the pre-edit snapshot still matches; changed content requires a fresh merge/retry, never a lost concurrent update. A missing hook may be created as a valid minimal script. A truncated/mismatched marker is repairable only when trusted ownership/snapshot evidence identifies the range safely; ambiguous foreign damage stays untouched and is reported.

The base manager installer adds no feature hook blocks or cron jobs. Dedicated setup/import manages integration only for its selected feature according to reviewed saved activation: DDNS/IP-Sync saved Off have no operational blocks/jobs; tunnel integration activates only after configured/enabled/health checks. Cloudflared's explicit maintenance-only install may separately install its guarded scheduler hook and enabled binary-updater job without completing tunnel setup. Merely opening a submenu never installs hooks, starts services, or changes remote resources.

Boot/WAN/DDNS/mount/watchdog/cron handlers never run a CFMgr package update check, prompt for an update, or reinstall the manager. Manager package updates are explicit actions; cloudflared's existing scheduled binary update remains a separate configured job.

| --- | --- | --- | --- |
| `Cloudflared` | `* * * * *` | `CFMgrWatchdog` | Register from trusted installed/configured/enabled state even without Entware; fired handler defers until mounted and readiness passes. No affecting quarantine; respect manual stop. No watchdog for unfinished/maintenance-only setup. |
| `CloudflaredUpdate` | `37 3 * * *` | `CFMgrCloudflaredUpdate` | Register from installed maintenance/explicit binary-update preference with no affecting quarantine, independently of mount/tunnel enable state. Each run checks mount before binary/network work; no active tunnel means update without starting one. |

Remove old Cloudflare jobs only after their commands/ownership are recognized and the new configuration is committed. In particular, the generic name `UpdateDDNS` alone is insufficient proof of ownership. Never remove BackupMon or unrelated jobs. Existing Cloudflare schedule defaults are retained unless explicitly changed in configuration.

CFMgr backups are manual only; do not register a backup job. On restore/repair, configured DDNS/IP-Sync data/settings remain saved, but operational blocks/jobs exist only while that feature is On. Disabled Cloudflared can retain healthy guarded integration; corruption/unfinished-commit quarantine suppresses its owned startup blocks/jobs until repair. Installed maintenance has a separate guarded schedule and binary-update preference. Actual jobs obey the activation table and health gate. A healthy disabled/unconfigured tunnel never starts while independently enabled binary maintenance may run; quarantined setup suppresses affected maintenance too. Turning off automatic binary updates removes only that updater job and preserves tunnel/watchdog selection.

Cron registration/dispatch is separate from permission to execute Entware-dependent work. Saved eligible cron jobs continue to fire while the drive is absent; JFFS handlers check health/enable state, then per-feature prerequisites. Cloudflared/updater return promptly without downloads, binary access or `/opt` writes until the actual Entware mount is ready; mount disappearance does not delete their otherwise eligible cron entries. DDNS/IP-Sync execute with verified firmware tools/JFFS/RAM regardless of Entware, emitting native messages and skipping unavailable custom logging. Matching post-mount and later ticks resume only eligible deferred work; no trigger enables or restarts every service blindly. A missing drive never holds router boot in a wait loop.

## Installation layout and Entware checks

The core manager, DDNS and IP-Sync require firmware tools/JFFS/RAM only. Entware is optional until Cloudflared binary/tunnel work or Scribe/logrotate custom file logging is selected. Keep persistent small settings/credentials/ownership/recovery in JFFS, frequent state/queues in RAM, and binary/tunnel/log data on verified Entware. The current tunnel setup uses `/opt/bin/cloudflared` and `/opt/etc/cloudflared`; that layout is not a dependency for the other two features.

CFMgr's settings file will be `/jffs/addons/cfmgr.d/config`, following the add-on convention used by [vpnmgr](https://github.com/h0me5k1n/vpnmgr/blob/main/vpnmgr.sh) and [Scribe](https://github.com/AMTM-OSR/scribe/blob/master/scribe.sh). CFMgr's small settings/helper files share this dedicated directory. Merlin documents `/jffs/configs` for firmware configuration overrides; CFMgr's own settings are read by the manager. See [Merlin custom config files](https://github.com/RMerl/asuswrt-merlin.ng/wiki/Custom-config-files).

### Required preflight

1. For every action confirm supported Merlin/root/JFFS user scripts, safely parsed config/health, native commands and sufficient writable space in the actual affected JFFS/RAM scope. Base manager/DDNS/IP-Sync do not probe or require opkg/Entware.
2. Resolve native curl/utilities/trust independently of `/opt` PATH, `LD_LIBRARY_PATH` or CA overrides; verify required options and fail only the unsupported selected action. No TLS bypass or silent Entware dependency for core features.
3. Only for Cloudflared/binary maintenance or custom logfile/Scribe work resolve `/opt` symlinks and actual mount identity. A directory/symlink/executable alone is insufficient; require expected persistent mounted writable Entware, not rootfs/JFFS/tmpfs.
4. Entware package installation additionally requires `/opt/bin/opkg` and the verified feed/version/ABI. Check scope-specific space/permissions before files/downloads/extraction and recheck the mount before every `/opt` commit; never write to a disappeared drive's leftover mountpoint.
5. For an explicit Cloudflared install/setup action with missing Entware, stop that action and explain amtm installation/mounting. Other menus/DDNS/IP-Sync remain usable. Missing Entware/Scribe during native setup just leaves custom logging unavailable; CFMgr never installs Entware, repartitions, or formats storage.
6. JFFS boot hooks register saved eligible cron entries regardless of mount; each fired handler checks its own prerequisites. Cloudflared/update/logging defer promptly until mounted. DDNS/IP-Sync may work with firmware tools/JFFS/RAM without custom files; no boot sleep/polling loop or substitute storage. Matching post-mount/later ticks retry eligible deferred scope only.
7. Backup/restore check the chosen mounted backup drive independently. Native-only payloads need JFFS/RAM plus that drive; archives with required Cloudflared/Entware payload also require mounted Entware. Core recovery/update/setup transactions do not require a backup drive.
8. Keep user Off/stopped and quarantine distinct from storage/network waiting. Existing eligible cron triggers do not bypass any execution gate, erase preferences or start unrelated services.

Read JFFS settings and render menus/status without Entware. Apply its mount requirement only to the affected Cloudflared/custom-log scope; absence does not reset configuration or block native work. Core rollback copies are small/bounded JFFS files, temporary work and DDNS/IP-Sync observations are RAM, and large tunnel data/logs remain Entware. Backup destination setup is optional; frequent state writes never become frequent JFFS writes.

### Shared public IPv4 resolver

Implement one small bundled POSIX/firmware core helper for WAN selection, IPv4 parsing/public-address validation, NAT/source selection and bounded external discovery. Both features call that same implementation; DDNS adds DNS work/completion, while IP-Sync adds list work only. The helper requires no DDNS account/configuration, Entware or Python. Do not copy a resolver/classifier/endpoint loop into each feature or make IP-Sync call a full DDNS update command just to obtain an address.

Use the selected WAN's verified native address, normally `wan<N>_ipaddr`, with actual firmware/interface/PPPoE mapping proved in P1. Classify standards-defined ranges: [RFC 6598](https://www.rfc-editor.org/rfc/rfc6598) allocates `100.64.0.0/10` for shared space; [IANA's IPv4 special-purpose registry](https://www.iana.org/assignments/iana-ipv4-special-registry/) identifies private and other special-use ranges. These are universal protocol constants, never an ISP's customer/public CIDR or an account-specific address. Handle registry exceptions correctly rather than blindly treating every special-purpose prefix as non-public.

The inspected Skynet `Is_PrivateIP()` in `IPSet_ASUS/firewall.sh` classifies non-public addresses and warns about bridge mode/CG-NAT; it does not compare an external address or prove carrier ownership. Non-public WAN or an external mismatch determines that external discovery is needed. Record `nat_state` as true/false/unknown with its evidence/reason; identify shared-range indication separately from private/double-NAT or observed mismatch. Do not claim a universal carrier-NAT proof or turn a failed check into false. CGNAT/upstream NAT does not prevent publishing an externally observed public IPv4, but does not make inbound IPv4 services reachable.

| WAN / evidence | Shared resolution behavior |
| --- | --- |
| RFC 6598 shared-space WAN | Indicate likely CGNAT/shared addressing and use bounded external IPv4 discovery. Never publish the router's shared address. |
| RFC 1918 private WAN | Indicate upstream NAT/private WAN and use the same external discovery path. Do not claim the carrier rather than a local modem owns it. |
| Valid public WAN with matching fresh external evidence | Infer no address translation observed; return the native WAN address. Reuse a still-valid direct-WAN observation without another HTTP request. |
| Valid public WAN differs from correctly routed external IPv4 | Indicate observed upstream translation/mismatch and use the validated external result. This covers NAT arrangements a private/shared-range-only test would miss. |
| New/changed WAN, boot, expired cache or source-policy change | Revalidate through bounded selected-WAN external observation before assigning direct/NAT state. A public-looking address alone is insufficient proof of no upstream NAT. |
| Disconnected/invalid WAN, failed external check, invalid/non-public/oversized discovery reply or unverifiable egress | Return a bounded unavailable/unknown result; leave DNS/list contents unchanged. Never fall back to publishing a private/shared address, another WAN/VPN exit or an unverified stale observation. Distinguish source failure from provider API failure. |

External requests must use IPv4 and the intended WAN egress; routing through a VPN/proxy/other WAN cannot silently determine this router's published WAN address. Endpoints, ordered fallback and time/size bounds are shared config. P1 must prove native egress selection and tool support; no added dependency or insecure TLS fallback. Only publish a strictly validated public IPv4. IPv6/AAAA remains a separate explicit source policy.

| Producer / trigger | Dispatch and optimization contract |
| --- | --- |
| Enabled DDNS invocation | Resolve once, pass the same immutable validated observation to enabled IP-Sync asynchronously, then perform DNS work and the appropriate firmware completion. DNS/API failure does not invalidate a successfully resolved address; list failure does not affect DNS completion. |
| IP-Sync without enabled DDNS | Invoke the common resolver only, then enqueue/list-sync that address. No DDNS setup, DNS lookup/write or DDNS completion callback. |
| Reviewed first enable, boot/recovery/restore, matching WAN-connected/reconnected or explicit update/publish | Request a coalesced detached discovery under feature/health/network gates. Manager launch, status and local hook self-heal remain read-only/no-network; a completed enable transaction schedules work rather than blocking the menu on HTTP. |
| Shared discovery cron | One job while either native feature is On, proposed every five minutes. Recheck externally often enough to detect upstream public-IP changes while router WAN stays unchanged; fresh observations dispatch only eligible changed/unsatisfied feature work. Preserve the separate daily DDNS refresh and Access saved-IP retry. No duplicate per-feature discovery schedules. |
| Saved-IP retry / both native features Off | Retry uses its queued validated address and never calls discovery. Both Off removes shared discovery integration; disabling DDNS alone leaves standalone IP-Sync discovery, and disabling IP-Sync leaves DDNS operational. |

Use one bounded private RAM observation cache and nonblocking/coalesced resolver lock. Key it by boot, selected WAN/native address, relevant source/routing policy generation and monotonic freshness; invalidate on matching WAN/source changes. Recheck that generation/egress before publishing an observation or enqueuing work; discard late replies from an old WAN/policy and retain a newer coalesced request. Reuse only fresh compatible observations; NAT egress observations must expire/recheck even when NVRAM is unchanged. Share snapshots across DDNS/IP-Sync/cron/manual overlap, never persist ticks/cache in JFFS, and keep provider workers/credentials/completion semantics separate. Tests must prove one discovery/HTTP sequence for a shared observation, no redundant lookup on a valid native/cache fast path, fresh standalone recovery, and bounded failures. Cache/cadence/total-budget defaults and actual native routing evidence are P1 work; this is selected design, not implemented performance proof.

| Current CFMgr direct-file design | Retain it: daemon output remains file-only, separate from brief native notices. uiScribe viewing needs an additional supported discovery mechanism. |
| Existing syslog-ng destination discovery | Can expose a declared destination without changing uiScribe. Using it for direct-file registration would require additional Scribe configuration/validation; do not fake unused destinations or change logging architecture solely to satisfy the viewer. Not selected. |

The [viewer](https://github.com/AMTM-OSR/uiScribe/blob/v1.4.14/Main_LogStatus_Content.asp) uses log basenames and warns about files over 4 MB; the backend can change parent-directory permissions. Any extension needs bounded viewing, unique labels, owned-path checks, private/redacted data, safe clear/rotate actions, and rotation/reinstall tests. Our proposed cloudflared `10M` policy therefore cannot promise full-file WebUI loading; do not silently change it for uiScribe. This is source research only; installed version and live WebUI access remain unverified.

## Backup and restore

Backup setup is optional. Keep the one complete manual format/root-level `CFBackup`/newest 3–5 retention (proposed 5); prune only after verified new creation, with no schedules/calendar tiers. Any selected mounted drive is valid, including one without Entware. Native-only manager/DDNS/IP-Sync archives and core restore need JFFS/RAM plus that drive, not Entware. Mounted Entware is additionally required only when the selected complete payload contains required Cloudflared/maintenance/declared tunnel files; optional custom-log history is handled explicitly below.

Use gzip-compressed tar (`.tar.gz`) through stock firmware commands. The captured [BackupMon source](https://github.com/ViktorJp/BACKUPMON/blob/main/backupmon.sh) uses `tar -zcf` for creation and `tar -tzf` for verification (captured `jffs/scripts/backupmon.sh`, lines 4570–4575 and 4597–4604). Validate those capabilities on supported firmware before release; do not require ZIP, GNU tar, or BackupMon itself.

| No usable drives / cancellation | Explain an empty/unusable list and return to the menu. Invalid entries are retried; `e`/Ctrl+C cancel without changing the destination or creating an archive. |
| Select restore source | Let the user use the configured destination or choose another mounted drive, then list recognized CFMgr archives from its `CFBackup` folder. A restore source selection does not silently change the saved backup destination. |
| Select archive | Show a short vertical numbered list of archive filenames/labels, newest first, using the router's local date/time and selected date order. After selection, show manager version, configured/enabled states, verified manifest, and intended changes; then confirm restore. Empty lists and cancellation return cleanly. |

### Archive dates and rolling retention

| Item | Initial behavior |
| --- | --- |
| Date/time source | Use router local time/timezone. Prefer an actual firmware-reported date format when available; verify this in P1. Do not infer date order from timezone/country guesses. If no reliable regional format is exposed, let the user choose day-month-year, month-day-year, or year-month-day during backup setup. |
| Archive filename/label | Use the exact prefix `CFbackup-` with the chosen regional date order and hyphens within date/time. First backup that local day: `CFbackup-08-10-26.tar.gz` for day-month-year or `CFbackup-10-08-26.tar.gz` for month-day-year. Another backup the same day adds `_hh-mm-ss`, for example `CFbackup-08-10-26_21-45-12.tar.gz`. These are examples, not the current router clock. |
| Same-day/collision check | Identify existing same-day archives in the backup set using saved local calendar-date metadata, including after a display-format change. Add the time suffix for subsequent backups; never overwrite an existing filename. An exact timestamp-name collision fails clearly so the manual action can be retried with a distinct time. |
| Sorting/age | Save a numeric creation timestamp/UTC reference, local calendar date, and display-format/timezone metadata in the manifest. Order/prune by saved creation order, never lexicographically by localized names; preserve correctness across date-format changes and daylight-saving repeats. |
| Count | `backup_keep` accepts 3, 4, or 5; proposed default 5. Count completed recognized archives in the current backup set, not staging files, unrelated files, or another set's archives. No per-day/week/month rules. |
| Purge timing | Verify/commit the new archive first, then remove oldest owned archives until the limit is met. Failed/cancelled/full-disk backups never delete a usable old backup to make room. A failed purge reports that the new archive exists but retention cleanup remains pending. |

The restore list needs only numbered archive labels initially; detailed feature/log/compatibility information appears after selection. A local archive filename is a label, not the source of restore state or retention age.

### Backup transaction

1. The user explicitly starts a manual backup. If no destination is configured, offer the numbered drive setup; cancellation creates nothing.
2. Verify JFFS/RAM core source and the selected backup mount, space/permissions and native tar/gzip. Require/check Entware source only for inventoried required tunnel/maintenance files or eligible custom history. A native-only backup works on a drive without Entware. Recheck each actual mount before final writes; no stale mountpoint fallback.
3. Acquire documented maintenance/backup locks and verify a coherent committed configuration generation. Defer backup while a setup/update/restore transaction is active, incomplete, or quarantined; offer repair rather than archiving damaged active setup as complete. Capture a consistent owned file set and permissions; coordinate eligible log capture with writers/Scribe rotation without an unnecessary tunnel restart.
4. Create a versioned manifest with creation timestamp/order, local calendar date/display-format/timezone metadata, backup-set identity, committed generation, manager/schema/archive versions, architecture, configured/enabled/stopped states, selected/pending tunnel method, maintenance-installed/binary-update states/provenance, file inventory/modes/hashes, and log-inclusion result. Required files missing from a completed feature/maintenance installation cause failure. Explicitly inactive drafts within an otherwise healthy committed setup can be included as drafts; they are distinct from an interrupted active commit and never mark a tunnel configured. Keep credentials in private payload files, not the display summary.
5. Build a uniquely named `.tar.gz` through stock firmware tools, using a private temporary archive on the selected backup filesystem. Store only relative paths in the archive, mapped to approved restore roots by the manifest.
6. Verify archive readability and the manifest/payload hashes, recheck the backup mount, then atomically rename the temporary archive to its final name in `CFBackup`. Report the archive path and included modules/log status only after success.
7. After successful verification/commit, enforce the saved 3–5 archive limit by purging only the oldest recognized completed archives in the same backup set on the verified mount. Keep the new archive and internal recovery material. Full disk, compression failure, mount loss, or cancellation before completion must not delete a usable old backup or silently omit required files; clean only this operation's owned temporary files. Report a retention cleanup failure separately from successful archive creation.

**Internal recovery is separate:** setup replacement, migration, manager updates, logging changes, and restore retain private transaction copies of files/integrations they may replace. These support interruption/failure rollback, do not create archives in `CFBackup`, and require no backup destination setup. Keep unresolved recovery material until the transaction is safely resolved; the binary updater's `.old`/pending recovery contract also remains intact. An additional user backup happens only through an explicit manual action.

### Feature-aware restore rules

Restore needs a small explicit state model, not guesses based on which tokens happen to be present. Validate that archive manifest and saved configuration agree about each module's setup and activation state.

| Saved feature state | Files and integrations to restore | Activation after restore |
| --- | --- | --- |
| Never configured | No module-specific setup, credentials, binary, or hook/job definitions are synthesized. Shared manager files still restore. Preserve an explicitly archived pending advanced draft/existing files when present; these are not completed tunnel setup. | Remains unconfigured/off; no dependency installation, feature hooks/jobs, service start, or API call. Draft completion still requires Re-detect config and reviewed activation. |
| Configured and enabled | Restore required owned files; check/re-inject each necessary owned hook block and retain its cron definitions. | Register active jobs and start/run the feature only after its validation/readiness checks. |
| Configured and disabled | Restore saved files, credentials, options, and inactive schedule definitions. DDNS/IP-Sync operational blocks/jobs remain absent; healthy Cloudflared can retain guarded integration. | Keep that feature's service/API jobs off. Cloudflared binary maintenance is governed by its separate saved preference below. Do not discard setup just because it was disabled. |
| Configured but saved as manually stopped | Restore configured integrations and the explicit stopped choice. | The watchdog/start hooks respect stopped state; no unexpected restart. |
| Cloudflared maintenance installed, no completed tunnel | Restore archived owned binary/helpers/provenance and maintenance settings, plus any explicitly archived advanced draft; no tunnel is synthesized. | Restore the binary-updater job only if its independent saved preference is on. No tunnel watchdog/start or logging policy until valid tunnel setup completes. |

The table's tunnel activation flags do not override the separately saved cloudflared binary-maintenance preference. For healthy configured but disabled/stopped tunnels, guarded tunnel hooks stay off; an independently enabled binary-updater job can still be restored without starting the tunnel. Disabled DDNS/IP-Sync retain all saved settings but have no operational blocks/jobs. Pending advanced files and maintenance installation are neither completed tunnel configuration nor evidence of an enabled connector. An invalid archive is rejected before commit; interruption during restore leaves the affected scope guarded until recovery establishes a complete valid generation.

| Example backup | Required restore result |
| --- | --- |
| Only DDNS was ever set up | Restore DDNS and shared manager files/integrations. Do not install/configure/start cloudflared or restore Access integration. |
| DDNS, tunnel, and Access were set up; only DDNS was enabled | Restore all three configurations/credentials; restore active DDNS integration and guarded disabled Cloudflared points, but no operational IP-Sync blocks/jobs. Activate DDNS only; restore cloudflared binary updates separately only if their independent maintenance preference was enabled. |
| Tunnel was configured but disabled; other features never set up | Restore its selected token/config method, folder/binary, and guarded integration points, retain tunnel disabled, and create no DDNS/Access setup. Preserve the independent binary-updater preference without starting the connector. |
| Only DDNS or IP-Sync was configured with eligible owned logs | Restore that feature's settings/status/log history and fixed policy, gated on Scribe/readiness and saved activation choices. No tunnel install/files or cloudflared-specific logging setup. |

When restoring over a different existing CFMgr setup, remove/deactivate only stale CFMgr-owned integrations for features absent from the chosen backup and stop a superseded owned connector when necessary. Preserve unrelated add-ons and files; do not purge old data merely because a feature is absent. Missing required payload/configuration is a restore validation failure, not a reason to invent new Cloudflare resources or silently change configured/enabled flags.

### Restore transaction

1. Select drive/archive and verify source mount, integrity, manifest/config agreement, package/schema, JFFS/RAM space and affected architecture. Required tunnel/maintenance/declared Entware payload additionally needs its mounted destination; native-only core restore does not. Review any explicitly deferred optional log history before Save. Inspection changes nothing.
2. Inspect entries, then extract into bounded private scope-appropriate staging: RAM/JFFS core recovery for native payload; verified Entware for large tunnel/log payload. Strict allowlist/size bounds reject absolute/traversal paths, unsafe links/devices/conflicting duplicates or writes outside roots. Validate hashes/modes before commit.
3. Show configured/enabled/stopped states, eligible logs, target paths, and planned integration changes for review. Map storage to this router and resolve any saved backup destination explicitly; never recreate another router's old physical mount label automatically.
4. After reviewed Save, acquire maintenance/update/lifecycle locks in the documented order, write a fresh durable local restore guard/journal, and retain private verified recovery copies of the current files/integrations/state. Pause owned schedules while committing. Stop only an affected/superseded owned connector through the bounded controller; abort if it cannot stop safely. Respect the shared e/Ctrl+C save-point contract; no automatic user backup archive is created.
5. Restore core package/config/required native files through the JFFS recovery transaction; restore inventoried tunnel payload on mounted Entware only when required. Mixed payload needs recoverable cross-filesystem stages, not an assumed atomic cross-filesystem rename. Preserve modes/off/stopped/selected method/drafts; transient token handoff derives from config only when needed. No mode inference from alternate files.
6. Reconcile separate exact CFMgr markers/jobs from saved state: enabled configured DDNS/IP-Sync receive their necessary operational blocks/jobs; disabled or never-configured DDNS/IP-Sync blocks/jobs are removed without clearing any saved settings. Healthy configured Cloudflared points retain disabled/stopped guards as applicable; independently restore maintenance only when archived installed/enabled state permits. Remove stale owned integration absent from both feature and maintenance state. Preserve foreign content/control flow/order, detect concurrent edits before atomic replacement, and preserve Scribe global files.
7. Restore eligible custom history only to mounted Entware and validate Scribe/rules before file output; explicitly deferred native-only log history remains in the archive and is reported. Preserve preferences/off choices and fixed DDNS/IP-Sync policies. Unavailable storage/Scribe leaves custom output inactive while native features/messages continue. Never-configured features get no logging; native-only restore installs no tunnel/Python components.
8. Validate remote references read-only where needed before activating enabled features or making provider writes. Preserve existing tunnels/DNS/Access policies; report revoked tokens/deleted resources and route repair through setup. Disabled features do not make API calls merely because their files were restored.
9. Validate the complete restored generation and durably commit it before clearing the local recovery guard. Resume only enabled, ready schedules/services and fresh DDNS/Access work, including independently enabled binary maintenance. Respect manually stopped tunnel state and selected mode; distinguish process survival from connectivity. Never-set-up features receive no fabricated setup; archived explicit maintenance/drafts restore without running a tunnel.
10. On activation failure, restore the saved local transaction, owned integrations, and prior activation state if they remain valid. An unresolved partial restore stays quarantined with affected starts/jobs blocked; preserve recovery copies and prompt repair on next manager launch. Report the failed stage and leave the selected user archive unchanged.
