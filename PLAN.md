Use stable comment identifiers such as `# CFMgr DDNS BEGIN` / `# CFMgr DDNS END`, with separate `IP-Sync`, `Cloudflared`, `Maintenance` and shared `NativeIPv4` blocks plus a private ownership manifest. The shared native block/job remains only while at least one valid DDNS/IP-Sync feature is On. This allows one feature to be removed without deleting another feature's calls. For example, the markers in a shared startup hook can look like this (illustrative; dispatch code is not implemented yet):

```sh
# CFMgr DDNS BEGIN
# CFMgr-owned DDNS startup/scheduler dispatch goes here.
# CFMgr DDNS END
```

Re-running install/repair must not duplicate blocks. Remove/replace only the exact identified CFMgr-owned block; never replace a whole populated hook, strip all matching words, or delete another add-on's markers. Preserve unrelated content, shebang, argument forwarding, existing branch/exit/return behavior, executable mode, and POSIX shell syntax. Choose a reachable insertion point instead of appending after an existing exit. Stage edits, syntax-check the complete hook, compare its current content again under the appropriate lock, and atomically replace only when the pre-edit snapshot still matches; changed content requires a fresh merge/retry, never a lost concurrent update. A missing hook may be created as a valid minimal script. A truncated/mismatched marker is repairable only when trusted ownership/snapshot evidence identifies the range safely; ambiguous foreign damage stays untouched and is reported.

Fresh base installation adds no feature blocks/jobs; first installation after retained-config removal uses the reconstruction contract below. Dedicated setup/import manages only selected eligible integration. DDNS/IP-Sync Off have no operational blocks/jobs; Cloudflared runtime requires configured+enabled and maintenance requires maintenance_enabled. Explicit maintenance install can activate updater maintenance while tunnel stays Off/unconfigured; a later explicit Off clears both activation flags. Merely opening menus/status never installs, downloads, enables or changes remote resources.

Boot/WAN/DDNS/mount/watchdog/cron handlers never run a CFMgr package update check, prompt for an update, or reinstall the manager. Manager package updates are explicit actions; cloudflared's existing scheduled binary update remains a separate configured job.

Remove old Cloudflare jobs only after their commands/ownership are recognized and the new configuration is committed. In particular, the generic name `UpdateDDNS` alone is insufficient proof of ownership. Never remove BackupMon or unrelated jobs. Existing Cloudflare schedule defaults are retained unless explicitly changed in configuration.

CFMgr backups are manual only. Restore/repair rebuilds current-code integrations from activation flags, never archived script bodies/commands. Explicit Cloudflared Off removes ALL owned runtime/start/WAN/mount/watchdog/updater/service blocks/jobs; installed files and update preference remain. Later explicit maintenance-only installation can activate only maintenance. Healthy repair follows these flags; corruption or uninstall/reset intent suppresses affected execution/reconstruction until resolved. Turning off automatic binary updates removes only its updater job, preserving tunnel/watchdog activation.

Due dispatcher coalesces newest work without defeating server delay; matching mount resumes only eligible scope, no blind enable/start or boot wait. Auth-Off records fault then removes affected operational integrations under shared guard, preserving logging rotation independently.

## Installation layout and Entware checks

The core manager, DDNS and IP-Sync require firmware tools/JFFS/RAM only. Entware is optional until Cloudflared binary/tunnel work or Scribe/logrotate custom file logging is selected. Keep persistent small settings/credentials/ownership/recovery in JFFS, frequent state/queues in RAM, and binary/tunnel/log data on verified Entware. The current tunnel setup uses `/opt/bin/cloudflared` and `/opt/etc/cloudflared`; that layout is not a dependency for the other two features.

CFMgr's settings file will be `/jffs/addons/cfmgr.d/config`, following the add-on convention used by [vpnmgr](https://github.com/h0me5k1n/vpnmgr/blob/main/vpnmgr.sh) and [Scribe](https://github.com/AMTM-OSR/scribe/blob/master/scribe.sh). CFMgr's small settings/helper files share this dedicated directory. Merlin documents `/jffs/configs` for firmware configuration overrides; CFMgr's own settings are read by the manager. ### Required preflight

1. For every action confirm supported Merlin/root/JFFS user scripts, safely parsed config/health, native commands and sufficient writable space in the actual affected JFFS/RAM scope. Base manager/DDNS/IP-Sync do not probe or require opkg/Entware.
2. Resolve native curl/utilities/trust independently of `/opt` PATH, `LD_LIBRARY_PATH` or CA overrides; verify required options and fail only the unsupported selected action. No TLS bypass or silent Entware dependency for core features.
3. Only for Cloudflared/binary maintenance or custom logfile/Scribe work resolve `/opt` symlinks and actual mount identity. A directory/symlink/executable alone is insufficient; require expected persistent mounted writable Entware, not rootfs/JFFS/tmpfs.
4. Cloudflared direct installation requires verified persistent Entware storage, supported architecture/ABI, official asset digest and native HTTPS/SHA256/metadata tools, not opkg/feed availability. Check scope space/permissions before staging/extraction and recheck mount before every `/opt` commit; never write to a disappeared drive's leftover mountpoint.
5. Recheck the expected Entware volume before every storage-dependent Cloudflared stage and during owned child supervision, not only at final write. If it vanishes, boundedly interrupt/reap only this action's owned child, retain incomplete guard/recoverable evidence and return to the menu: drive/mount unavailable, Cloudflared action stopped. For an in-flight create, warn a failed tunnel may exist and direct manual Zero Trust inspection/deletion before explicit retry after the SAME expected mount is verified again. Do not wait in boot/menu, write to a leftover mountpoint or automatically repeat creation. Status, e, public Off/unhook/safe owned stop and native features still work from JFFS/RAM.
6. For an explicit Cloudflared install/setup action with missing Entware, stop that action and explain amtm installation/mounting. Other menus/DDNS/IP-Sync remain usable. Missing Entware/Scribe during native setup just leaves custom logging unavailable; CFMgr never installs Entware, repartitions, or formats storage.
7. JFFS boot hooks register saved eligible cron entries regardless of mount; each fired handler checks its own prerequisites. Cloudflared/update/logging defer promptly until mounted. DDNS/IP-Sync may work with firmware tools/JFFS/RAM without custom files; no boot sleep/polling loop or substitute storage. Matching post-mount/later ticks retry eligible deferred scope only.
8. Backup/restore check the chosen mounted backup drive independently. Native-only payloads need JFFS/RAM plus that drive; archives with required Cloudflared/Entware payload also require mounted Entware. Core recovery/update/setup transactions do not require a backup drive.
9. Keep saved Off, installation/removal guards and quarantine distinct from storage/network waiting. Eligible cron never bypasses execution gates, erases preferences or starts unrelated services.

Read JFFS settings and render menus/status without Entware. Apply its mount requirement only to the affected Cloudflared/custom-log scope; absence does not reset configuration or block native work. Core rollback copies are small/bounded JFFS files, temporary work and DDNS/IP-Sync observations are RAM, and large tunnel data/logs remain Entware. Backup destination setup is optional; frequent state writes never become frequent JFFS writes.

### Shared public IPv4 resolver

Implement one small bundled POSIX/firmware core helper for WAN selection, IPv4 parsing/public-address validation, NAT/source selection and bounded external discovery. Both features call that same implementation; DDNS adds DNS work/completion, while IP-Sync adds list work only. The helper requires no DDNS account/configuration, Entware or Python. Do not copy a resolver/classifier/endpoint loop into each feature or make IP-Sync call a full DDNS update command just to obtain an address.

Use the selected WAN's verified native address, normally `wan<N>_ipaddr`, with actual firmware/interface/PPPoE mapping proved in P1. Classify standards-defined ranges: [RFC 6598](https://www.rfc-editor.org/rfc/rfc6598) allocates `100.64.0.0/10` for shared space; [IANA's IPv4 special-purpose registry](https://www.iana.org/assignments/iana-ipv4-special-registry/) identifies private and other special-use ranges. These are universal protocol constants, never an ISP's customer/public CIDR or an account-specific address. Handle registry exceptions correctly rather than blindly treating every special-purpose prefix as non-public.

The inspected Skynet `Is_PrivateIP()` in `IPSet_ASUS/firewall.sh` classifies non-public addresses and warns about bridge mode/CG-NAT; it does not compare an external address or prove carrier ownership. Non-public WAN or an external mismatch determines that external discovery is needed. Record `nat_state` as true/false/unknown with its evidence/reason; identify shared-range indication separately from private/double-NAT or observed mismatch. Do not claim a universal carrier-NAT proof or turn a failed check into false. CGNAT/upstream NAT does not prevent publishing an externally observed public IPv4, but does not make inbound IPv4 services reachable.

| WAN / evidence | Shared resolution behavior |
| --- | --- |
| RFC 6598 shared-space WAN | Indicate likely CGNAT/shared addressing and use bounded external IPv4 discovery. Never publish the router's shared address. |
| RFC 1918 private WAN | Indicate upstream NAT/private WAN and use the same external discovery path. Do not claim the carrier rather than a local modem owns it. |
| Valid public WAN with matching fresh external evidence | Infer no address translation observed; return the native WAN address. Reuse a still-valid direct-WAN observation without another HTTP request. |
| Valid public WAN differs from correctly routed external IPv4 | Indicate observed upstream translation/mismatch and use the validated external result. This covers NAT arrangements a private/shared-range-only test would miss. |
| New/changed WAN, boot, expired cache or source-policy change | Revalidate through bounded selected-WAN external observation before assigning direct/NAT state. A public-looking address alone is insufficient proof of no upstream NAT. |
| Disconnected/invalid WAN, failed external check, invalid/non-public/oversized discovery reply or unverifiable egress | Return a bounded unavailable/unknown result; leave DNS/list contents unchanged. Never fall back to publishing a private/shared address, another WAN/VPN exit or an unverified stale observation. Distinguish source failure from provider API failure. |

External requests must use IPv4 and the intended WAN egress; routing through a VPN/proxy/other WAN cannot silently determine this router's published WAN address. Endpoints, ordered fallback and time/size bounds are shared config. P1 must prove native egress selection and tool support; no added dependency or insecure TLS fallback. Only publish a strictly validated public IPv4. IPv6/AAAA remains a separate explicit source policy.

| Producer / trigger | Dispatch and optimization contract |

Proposed launch budget remains under one second when healthy, with at most two seconds of foreground check/repair across all three integrations; measure in P8. Use nonblocking locks and bounded validation; contention defers instead of waiting. Background hooks never prompt. ### Feature-aware restore rules
