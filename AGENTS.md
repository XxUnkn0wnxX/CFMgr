# CFMgr project instructions

- Develop on `develop`; reserve `main` for stable releases.
- CFMgr is CLI-only. A browser GUI is an optional future idea outside the approved roadmap and completion percentage; implement or schedule one only after explicit user direction.
- For each small coherent implementation batch, run focused tests and relevant lint/static checks, review, then commit locally. Accumulate those commits and push to `develop` only at each approximately one-percentage-point increase in overall implementation completion (for example, 30%, 31%, 32%); do not push each smaller batch. Each 1% publication checkpoint requires the full local suite, test-cost review and fixes until green before pushing the tested commits. Wait for CI; fix and repush failures within that same checkpoint until CI passes before beginning the next set of batches. Include checkpoint documentation/handoff publication in that checkpoint; do not create separate routine pushes between 1% milestones. Percentages estimate delivered requirements, not commit counts or elapsed time; finish coherent work without inflating progress to trigger a push. Do not repeat the full suite for every small commit. Never promote runtime code to main or deploy without separate authorization.
- Follow the scope, stage and next actions in [PLAN.md](PLAN.md), including its every-10% test/documentation review and handoff checklist; host/CI validation does not authorize live deployment or router changes.
- Continue through authorized implementation packages and 1% publication checkpoints without ending the turn, until each ten-percentage-point milestone (30%, 40%, and so on). Treat every 10% marker as a handoff for a new session unless the user explicitly overrides it. Finish the coherent package and its full local/publication/green-CI gate, finalize the documentation audit from the accepted code, record a clean resumable handoff in PLAN.md, and pause. Record exact commits, validation results/skips, worktree and agent state, unresolved findings and next actions; leave no required command or worker active. Resume only on the user's instruction. Give progress updates and record each checkpoint in PLAN.md. On an earlier user pause/stop request, finish the nearest safe agreed checkpoint, record the handoff, and stop before starting another package.
- Apply the global `zr0-parallel-execution` and `zr0-test-efficiency` skills for their coordination and testing procedures. This repository explicitly authorizes concurrent independent work across sessions; use PLAN.md as the existing parent-owned master plan. The project-specific routing, package limits, validation gates and safety rules below remain in force.
- CFMgr-only delegation override: the following routing takes precedence over the global routing while working in this repository. Do not apply it to other projects or change the global AGENTS.md or agent profiles to match:
  - Use `worker_strong` (GPT-6.1 Sol) for substantial runtime implementation, cross-file changes and work involving process ownership, interruption, storage safety or uncertain compatibility. Keep tightly coupled implementation and essential regression tests in one coherent package when splitting would duplicate context or create integration risk.
  - Use `worker` (GPT-6 Luna) for bounded test implementation, fixtures, routine refactors, supporting work and simpler runtime functions with clear contracts. Parallelize independent code/test work only with separate file ownership. Test design must prove distinct behavior; the parent reviews what each test actually establishes. Use Sol follow-up review/fixes where complexity or risk warrants it, rather than requiring a second full implementation pass for every Luna package.
  - Prefer concurrent implementation and test construction when a stable shared contract makes them independent: Sol owns substantial runtime files and Luna owns tests/fixtures. Independent small stages/substages may also progress together. Normally keep at most two active implementation packages; allow a third only when interfaces/dependencies are settled and integration stays easy to track. Follow the parallel-execution skill for exclusive ownership, briefs, dependency tracking and separate integration gates, recording these in PLAN.md before launching. Finish the active set before its combined full-checkpoint push/CI gate. On pause/stop, start no more packages and record the nearest safe checkpoint.
  - At each stage/commit boundary, the parent reconciles code/test discrepancies against the agreed contract and source evidence, integrates the result, and requires focused checks plus relevant static validation before committing. Never weaken a test merely to match the implementation or assume the implementation is wrong merely because a test fails. Tiny, understood discrepancies may be fixed by the parent or `worker_alt` after explicit ownership transfer; broader fixes stay with the appropriate worker. The parent handles difficult judgement and may use `deep` for an exceptional ambiguous or critical discrepancy when the active profile provides it, rather than adding a mandatory extra review to every commit. Follow the normal major-checkpoint full-suite/CI gates.
  - Use `worker_alt` (Luna Low Fast) opportunistically for tiny, fully specified, mechanically bounded code/test fixes when its fast turnaround saves time. Do not spend more on a handoff than the fix requires; the current owner or parent may be faster. If the Fast lane is unavailable or the task grows, use `worker` (or Sol for substantial judgement); do not repeatedly retry the Fast lane.
  - Keep `explorer` to quick, bounded, read-only code passes and lightweight reviews. It does not implement, run tests or own extended investigations. The parent handles deeper investigation/judgement and may use `analyst` for difficult independent review/debugging or `deep` for an exceptional critical problem when the active profile provides it. Custom workers must not spawn further agents.
  - The parent owns architecture, security-sensitive judgement, integration and final review. It owns documentation coordination and may either write the docs itself or assign a dedicated documentation worker after milestone code finalization, with exclusive file ownership and parent review. It may directly make tiny, well-understood runtime or test fixes when ownership is clear and no worker is editing those files, then run the relevant focused checks. Broader or uncertain implementation/fixes belong with the appropriate worker. Transfer ownership explicitly; never overlap writers or escalate solely because one test failed.
  - The parent or implementation worker launches tests. Hand already-running long test/CI jobs to `awaiter` for waiting/polling through terminal completion and concise result reporting. Its configured role is monitoring only: it does not launch, diagnose, edit or rerun work. Keep very short focused checks with their owner when delegation would add overhead. Pass shared log/exit paths because terminal session IDs may not be accessible across agents.
  - Never overlap writers. Inspect existing agent threads on resume, integrate completed findings, and reuse appropriate threads. Keep the active runtime/profile authoritative; if a requested role/model is unavailable, disclose that instead of silently claiming it was used.
- Keep feature modules (Cloudflared, DDNS, IP-Sync and diagnostics) directly in `modules/`, and shared core libraries/parsers in `modules/lib/`. Put supporting workers, updaters and dependency bootstrap in `modules/helpers/`; use `modules/hooks/` for thin firmware-hook/cron entry scripts and integration templates. Keep feature logic in its owning module, reuse shared code through `modules/lib/`, and preserve installed hook destinations. Build future features as coherent modules with small explicit interfaces and thin menu/setup/dispatch integration; avoid scattered feature logic, copied shared helpers or arbitrary directory-based auto-loading. Package manifests/catalogs must preserve verified safe relative nested paths. The user authorizes sensible layout adjustments as implementation grows: classify new and existing files by responsibility (feature/core, helper/worker, hook/cron, supporting assets, tests, developer tools or docs), add purpose-specific subfolders when useful, and avoid a flat catch-all or unnecessary empty hierarchies. Update imports, callers, discovery/packaging and affected documentation together; review organization at milestones without requiring repeated permission.
- Developer environment: reuse the repository `.venv`; run `.venv/bin/python -m pip install -r requirements-dev.txt` only when setup/requirements require it. Python/pytest/Ruff/shfmt are developer tools, not router dependencies. ShellCheck is a separate host executable. See `docs/development.md` for setup and version details.
- Validation commands: focused `.venv/bin/python -m pytest tests/test_<area>.py` plus relevant Ruff, shell syntax, ShellCheck, shfmt and whitespace checks for a small batch; `.venv/bin/python tools/check.py` for the full major checkpoint. That runner is local only and never commits, pushes or watches Actions. GitHub CLI/authentication is needed for CLI publication/CI inspection, not for local validation.
- Apply the test-efficiency skill to local and CI coverage. Keep focused real-consumer tests, shared fixture code with fresh state, and a small representative integration set. Preserve meaningful failure, interruption, ownership, byte-framing and BusyBox compatibility evidence. Workers must explain the value of expensive new cases or broad reruns.
- Before each implementation package, reconcile its planned tests and fixtures with this strategy and update outdated test instructions in PLAN.md. Preserve distinct acceptance requirements; historical test counts and superseded fixture layouts are evidence, not targets to reproduce.
- Review test cost before every develop push and after roughly three local implementation batches, whichever comes first. Use the latest pytest duration report and recorded full-suite baseline; time only affected cases when more evidence is needed. Investigate new ordinary cases over about two seconds, integration cases over about five seconds, or a material upward trend (roughly 20% in comparable runs). These are review triggers, not permission to raise timeouts, skip failures or drop distinct safety coverage.
- When tests become slow, the parent or an analyst reviews recorded timings and duplicated setup; implement justified simplification before expanding coverage. Explorer may assist with a quick read-only pass only. Follow the test-efficiency skill, keep required BusyBox and distinct safety coverage, and aim for a full local suite measured in a few minutes. Record coverage changes and before/after timings in PLAN.md; do not add a second exhaustive run merely to measure cost.
- CI runs for eligible code/tooling/test pushes to `develop` and pull requests targeting `develop`; documentation-only changes skip it. Linux/BusyBox evidence is distinct from Merlin kernel/hardware acceptance. Do not widen CI to main or promote runtime code as a convenience.
- Planned distribution keeps `cfmgr.sh` and `catalog.txt` at repository root. Install only the CFMgr entry at `/jffs/scripts/cfmgr.sh`; its modules/support code and separate catalog belong under `/jffs/addons/CFMgr.d/`, preserving safe relative categories. Keep the developer flag/settings/credentials in extensionless `/jffs/addons/CFMgr.d/config`, generated from code-defined defaults on genuinely fresh router installation; do not ship a config file or template in the public repository. Check retained setup before defaults and preserve existing settings under validated migration. Full uninstall KEEP retains settings/catalog/recovery; explicit WIPE also removes the exact owned `/jffs/addons/CFMgr.d/` directory only after required safe cleanup completes. Preserve ownership/foreign-file/interruption guards and retain recovery evidence on incomplete cleanup. Reset retains the verified package and regenerates defaults. Developer mode preserves an existing router `catalog.txt` byte-for-byte during branch/commit switches, updates and force reinstalls; download the selected snapshot default only when the local file is absent. Source changes still acquire and activate one verified complete manager/module commit, never mixed revisions. Implement the installer/updater only under the applicable PLAN stage.
- Treat root `PLAN.md` as the sole design, checklist, progress record and handoff. Read it at session start and update decisions, checks, commits and next actions after each material package. Keep this file limited to standing repository guidance; stage-specific instructions, session history and resume/pause state belong only in the plan.
- Keep progress, planned work and validation history in PLAN only: no checkpoint percentages, acceptance labels, commit/run chronology, test totals or measured timings in the official guides. Write those guides in present tense for completed functionality, as normal finished-feature documentation; add, change or remove information as implementation grows. The README WIP table is the progress-overview exception. Preserve useful commands, actual API prerequisites/limitations, technical bounds, reproducible checks, standing workflow rules and visual polish, with detail proportionate to each guide. Remove speculative procedures, stale history and duplicated prose during each documentation pass.
- Finalize and review the milestone code before generating or updating its documentation. Assign the parent or one dedicated documentation worker/subagent as an explicit workstream, with exclusive file ownership and the finalized commit/snapshot recorded in PLAN.md. Once code is finalized, documentation may proceed alongside CI, validation or other independent tasks; do not write against an actively changing implementation. Any subsequent code fix requires a documentation reconciliation before publication. The parent integrates and reviews delegated documentation. PLAN.md design, ownership and progress records remain current throughout execution; this sequencing governs the milestone implementation guides.
- At every major milestone, and always before or at each ten-percentage-point checkpoint, audit and update all relevant repository documentation: README, development, architecture, compatibility, setup, contributing and fixture guides, plus PLAN.md. Keep completed behavior, usable commands/workflows and technical limitations accurate; record remaining work, progress and validation history only in PLAN, apart from the README WIP table. Add usage guidance when a feature is implemented and validated; never present planned commands as available. Reserve a separate end-to-end consistency and polish pass for 100% completion; do not defer useful documentation until that final pass. Record the audit and intentionally unchanged guides in PLAN.md. Include documentation in the checkpoint publication without creating extra routine pushes between 1% milestones. Keep the README feature-status table short and user friendly, directly below or near its warning, and include completed features alongside partial and planned work; detailed tracking stays in PLAN.md.

Estimate remaining implementation, validation and integration work honestly; distinguish user-run router acceptance from host/CI checks. Continue concise updates for material findings between milestones.
